## CI/CD 实操

### CI 是合代码就跑测试，CD 是版本随时可发甚至自动发

<Tweet id="2121709005093421410" />

**这是在说什么**

CI（持续集成）就像每天早会：开发一提交代码，系统立刻拉代码、编译、跑单元测试、扫漏洞，有问题当场拦住。CD（持续交付/部署）是让每次构建出来的镜像都‘拎包入住’——交付版只需人工点一下，部署版连点都不用。关键不是工具链多长，而是‘一个制品走到底’（不重打镜像）、‘任一环节失败即停’、‘出事一键回滚’。

**我们能学到什么**

- 别只配 Jenkins/GitHub Actions，先确保每次构建产物唯一且贯穿全环境
- 上线前必须验证回滚路径是否真实可用，不能只写在文档里
- 测试门禁不是摆设，要让单元测试真正能发现逻辑冲突

## Go 并发避坑

### Go 1.22 让 for 循环每次迭代生成新变量，根治 goroutine 捕获错值

<Tweet id="2123085728389439875" />

**这是在说什么**

以前 for 循环里起 goroutine，所有 goroutine 共享同一个循环变量（比如 user），等它们真正执行时，user 早被下一轮覆盖成最后一条数据。结果几千条英文推送全发成中文。Go 1.22 后，每次迭代自动创建独立变量副本，每个 goroutine 拿到的是自己那轮的值。本质是语言层把‘闭包捕获变量’这个易错点直接堵死。

**我们能学到什么**

- 升级 Go 1.22+ 后，不用再手动在循环内声明新变量（如 u := user）
- 老项目若未升级，grep 'go func.*for' + 单元测试并发场景，重点查变量捕获
- 这类问题无法靠静态检查发现，必须写并发测试用 time.Sleep 或 runtime.Gosched 触发竞态

## Agent 怎么落地

### 文档写‘不能访问密钥’没用，得靠权限控制和执行环境拦住

<Tweet id="2123237052594700596" />

**这是在说什么**

提示词说‘别碰生产密钥’，但只要 Agent 运行环境里有密钥文件或环境变量，它就能读。就像告诉小孩‘别碰刀’，却把菜刀放在他伸手可及的台面上。真正有效的是三层防护：代码层用 lint 禁 API、流程层用 CI 分支保护、运行层用最小权限容器+短期凭据+工具层审批。

**我们能学到什么**

- Agent 出错先问：这是该由模型判断的问题，还是本该被系统规则拦住的问题？
- 长期运行的 Agent 默认不该有本机 root 权限，哪怕在本地也要按需申请临时 token
- 敏感操作（删库、付款）必须拆成两步：模型建议 → 人工审批 → 工具执行

### Multi-Agent 不是越多越好，加一个 Agent 要算清 Token 成本和故障率

<Tweet id="2122586507659616495" />

**这是在说什么**

Sequential（顺序）、Parallel（并行）、Hierarchical（管理层级）这些模式本身没问题，但每多一层 Agent 就多一次模型调用、一次上下文传递、一次出错可能。比如 Manager Agent 委派任务，若它自己理解错目标，后面所有 Worker 都白干。真正的工程判断是：哪些步骤必须模型决策（如解析简历语义），哪些用确定性代码更稳（如校验邮箱格式）。

**我们能学到什么**

- 上线前必测：单 Agent 流程 vs 多 Agent 流程的 P95 延迟、Token 消耗、错误定位耗时
- 优先用 Workflow 引擎（如 Temporal）编排确定性步骤，只在模糊边界处插入 Agent
- 避免‘为架构而架构’——如果五步里四步能用 if/else 写完，别硬塞四个 Worker

### Always-on Agent 不等于常驻进程，而是任务存在、执行者按需唤起

<Tweet id="2124113594036170994" />

**这是在说什么**

像 Pi Bot 这类本地 Agent，不是开机就跑满 CPU，而是监听事件（如收到新邮件、检测到代码变更），触发时才拉起轻量进程干活，完事即退。核心是把‘状态’（任务清单、记忆、文件）存本地，把‘执行’（模型推理、工具调用）按需启动。这样既保隐私，又省资源。

**我们能学到什么**

- 设计本地 Agent 时，把持久化（磁盘存记忆）和执行（内存跑模型）彻底分离
- 唤醒条件必须明确可测（如文件修改时间戳、HTTP webhook payload），避免轮询耗电
- 用户无感知的‘后台运行’不是目标，可控、可中断、可审计才是

### Pi Bot 开源了：Bot 在你电脑上干活，工具调用全过权限关，命令在隔离环境跑

<Tweet id="2124106873729421365" />

**这是在说什么**

Pi Bot 把 AI 团队装进本地客户端：Bot 名字可自定义、能私聊/建群协作、改文件/跑命令。但它不信任任何一步——每个工具调用前都要过权限检查（比如删文件需二次确认）、所有命令在 sandbox 容器里执行、审批记录全落本地磁盘。相当于给每个 Bot 配了个保安+监工+记账员。

**我们能学到什么**

- 本地 Agent 的安全底线是：敏感操作必须显式授权，且授权不可绕过
- 隔离环境（sandbox）比‘本地运行’更重要，否则 Bot 仍可读取浏览器 Cookie 或 SSH 密钥
- 欢迎提 PR，但先看 pibot-roles 仓库里的角色模板——复用比从零设计更可靠

### Claude Code 不是聊天框，用 Hooks 能让它改完代码自动跑格式化和类型检查

<Tweet id="2124111081324839357" />

**这是在说什么**

Claude Code Ultimate Guide 这个项目把 AI 编程变成流水线：比如 PreToolUse Hook 可拦截危险命令（如 DROP TABLE），后置 Hook 能在模型改完文件后自动触发 go fmt + go vet。它不教你怎么写 prompt，而是告诉你怎么用脚本把模型‘套进规矩里’。

**我们能学到什么**

- 立刻在 .claude/settings.json 里配 UserPromptSubmit Hook，正则过滤 postgres://.*@ 和 api_key=
- 用 ADR（架构决策记录）模板统一管理 Hooks 修改原因，避免团队随意开关
- 安全审计清单要包含‘本地会话日志是否加密’和‘MCP 插件是否有沙盒’两条

### 新人把生产密码贴进 Claude Code，企业版协议不保命，本地日志和 MCP 串门才真危险

<Tweet id="2124171478677746151" />

**这是在说什么**

企业版承诺不拿数据训模型，但不等于密码安全：① 本地终端会话 JSONL 日志明文落盘；② 多 MCP 工具共用上下文，密码可能被模型顺手传给日志插件；③ 破窗效应——这次敢贴密码，下次就敢 commit 私钥。真正防线是工具链自动注入凭证（op run）+ 本地 Hook 拦截明文。

**我们能学到什么**

- 所有本地 AI 工具必须默认关闭明文日志，或对敏感字段做磁盘级加密
- 在项目根目录放 .claude/hook/pretool.js，用正则拦截 mysql://.*@、token=、sk_live_
- 技术主管要定期 audit 团队成员的 ~/.claude/history 目录，查高熵字符串

### Harness 不是越强越好，和模型适配度比绝对排名更重要

<Tweet id="2124026179212493000" />

**这是在说什么**

Harness（如 Pi、EvoX）是 Agent 的‘操作系统’：负责把模型输出转成工具调用（Action Realization）、失败后引导重试（Execution Continuity）、让结果描述匹配实际执行（Outcome Grounding）。但不同模型需要不同帮助——Sonnet 5 喜欢 Pi 的恢复机制，GLM-5.3 却更吃 EvoX 的参数修正。适配度不对，强 Harness 反而拖累。

**我们能学到什么**

- 选 Harness 前，先用目标模型跑 3 个典型失败 case（如工具参数错、网络超时、重复失败）
- 不要迷信论文总分，重点看你的主力模型在该 Harness 下的子项成功率
- 增加 Harness 机制（如加 verifier）前，先统计它在你业务中实际触发频次和收益

## 其他

### Long horizon Agent 的瓶颈在上下文效率和元决策能力

<Tweet id="2123994505951273296" />

**这是在说什么**

loopx 研究指出：长周期任务卡住，要么是上下文太臃肿（信息密度低），要么是模型不会‘想下一步该干什么’。前者靠结构化压缩（比如只存关键证据而非全文），后者靠预设元动作（grow 扩展搜索、switch 换策略、verify 交叉验证）。按常理理解是：AI 也需要‘工作笔记’和‘待办清单’。

**我们能学到什么**

- 长任务 Agent 必须支持动态裁剪上下文，保留证据链而非原始日志
- 在 prompt 里硬编码 (grow, switch, verify) 三动作，比泛泛要求‘思考下一步’更有效
- local verifier（当前步骤自查）和 global verifier（全局目标对齐）失配时，优先信 global

### 《Developer to Architect》对初级工程师太难，但值得三年后重读

<Tweet id="2123880585492115873" />

**这是在说什么**

这篇指南讲的是从写代码到定义系统边界的思维跃迁，涉及权衡取舍、技术债量化、跨团队说服。对刚毕业的人信息密度过高，当冷知识即可。它真正有用的地方是提供了一套评估自己成长阶段的 checklist：比如能否在没文档时画出服务依赖图，或解释为什么选 Kafka 而不是 RabbitMQ。

**我们能学到什么**

- 第一年聚焦‘把需求变成可运行代码’，第三年开始练习‘画图解释为什么这么设计’
- 遇到架构讨论先抄三句话：‘这个选择解决了什么问题’‘代价是什么’‘有没有更小的验证方式’
- 别急着读，等你亲手删过两次技术债、背过一次线上事故锅再打开
