不是看怎么搭 Demo，而是看怎么让系统在客户那儿跑稳。很多帖子都在讲一个事：模型越强，工程约束越不能松。比如权限、幂等、可观测、状态恢复——这些不是加分项，是上线前提。

> 收集区间：2026-11-08 – 2026-11-15（JST），共 16 条。

## 岗位现实

### AI 时代面试该考什么？别再问技术栈了

<Tweet id="2119238261080273132" />

**这是在说什么**

以前问「会哪些语言」还能筛人，现在 AI 能帮你用五种语言写 CRUD。真正要考的是：你有没有亲手修过模型输出格式错乱的 Bug？有没有处理过工具调用超时但实际已执行的脏数据？这些才是真实交付中天天踩的坑。

**我们能学到什么**

- 面试应聚焦具体故障场景，而非技术名词罗列
- 考察候选人是否写过 Pydantic 校验层或自修复逻辑
- 能说清一次失败请求的完整链路追踪路径，比背八股更有说服力

### 工程师护城河正在从技术转向「人的问题」

<Tweet id="2120961974519398535" />

**这是在说什么**

AI 擅长模式匹配，但搞不定产品定位、打动人心、商业闭环。比如同样做 SaaS，AI 能生成代码，但决定「为什么用户愿意付钱」「怎么让客户第一眼就想试」，还得靠人。这条信息量一般，当冷知识即可。

**我们能学到什么**

- 每周花 2 小时读用户反馈，比刷 10 篇论文更接近真实需求
- 学基础心理学（如损失厌恶、峰终定律），比学新框架更能提升转化率
- 和销售、客服定期对齐，比只和研发开会更能发现系统盲点

## RAG 怎么落地

### WeKnora 开源：让知识库自己更新不靠人

<Tweet id="2119266910684819920" />

**这是在说什么**

传统 RAG 像把书撕碎塞进抽屉，文档一改旧碎片就变垃圾。WeKnora 类似「带自动归档员的活档案馆」：它能识别文档版本、标记失效内容、主动触发重索引。不是换个向量库，而是给知识加生命周期管理。

**我们能学到什么**

- RAG 系统必须支持文档粒度的版本控制和软删除
- 知识入库环节要能区分「原始文档变更」和「语义变更」
- 评估 RAG 时，先看知识新鲜度，再看检索准确率

### RAG 不是大模型应用，是软件工程系统

<Tweet id="2119713865709797884" />

**这是在说什么**

RAG 的核心难点不在模型，而在文档解析（PDF 表格错乱）、切片（技术说明被截断）、检索（正确文档没召回）、权限（A 公司资料被 B 公司搜到）。就像修水管，漏水不是水龙头问题，是接头没拧紧。

**我们能学到什么**

- 调试 RAG 错误，优先查日志里的 retrieval 结果，再看模型输入
- 中小项目用 PostgreSQL + pgvector 足够，别一上来就上专用向量库
- 必须建评测集：固定测试问题 + 人工标注标准答案 + 检索召回率指标

## Agent 怎么落地

### Google 的大象金鱼插件：强制拆开设计和评审

<Tweet id="2119580092682883584" />

**这是在说什么**

大象（Elephant）是设计者，带着全部上下文写方案；金鱼（Goldfish）是评审者，只看方案和代码，故意不看历史对话——就像人脑记不住 7 个以上信息，它专揪那些没写进文档的隐含假设。本质是用架构隔离对抗认知偏差。

**我们能学到什么**

- 关键设计决策必须脱离对话上下文独立存档
- 评审阶段禁用历史消息，倒逼文档自包含
- 可用类似机制做 Prompt 审查：让另一个模型只读 Prompt 和输入，不看前序输出

### 斯坦福 CS329Z 中文版：从搭 Agent 到测 Agent

<Tweet id="2119653960936223035" />

**这是在说什么**

这不是理论课，是带 HW1 代码实操的工程课。比如第 5 讲教你怎么写一个能自动发现并修复工具调用参数错误的 agent，重点不是框架 API，而是如何把 LLM 的概率输出收敛成确定性调用。

**我们能学到什么**

- 动手做 HW1 比通读讲义重要十倍
- 重点学「评测设计」和「失败注入测试」两讲
- 离线单文件版可直接浏览器打开，适合地铁通勤时读

### Personal Agent 发消息原理很简单：发消息本身是个 Tool

<Tweet id="2120045358512550108" />

**这是在说什么**

把「发送消息」封装成一个可调用的 Tool（比如 send_message(text: str)），Agent 就能在执行其他任务的同时异步发消息。就像人边开会边回微信，不是靠魔法，是靠把动作标准化。

**我们能学到什么**

- 所有外部交互都应抽象为 Tool，包括发消息、写 DB、发邮件
- Tool 必须定义明确输入输出，且支持幂等标识
- 避免在 Agent 内部硬编码通信逻辑

### 校验 LLM 输出不能靠 Prompt 强调，得用 Pydantic 硬约束

<Tweet id="2120000242750009647" />

**这是在说什么**

Prompt 是软提醒，Pydantic 是红绿灯。比如模型返回 &#123;"user_id": "abc"&#125;，但字段要求是 int，校验层就该直接报错并触发 self-correction，而不是让下游服务崩溃。这是把概率输出变成确定性 API 的关键一步。

**我们能学到什么**

- 所有 Tool Call 输入必须走 Pydantic 或 JSON Schema 校验
- 校验失败时，构造清晰错误信息喂回模型，而非抛异常
- 兜底规则（如默认值、降级逻辑）必须显式编码，不能依赖模型猜测

### Agent 系统不是 LLM 加工具，是带权限和审计的运行时

<Tweet id="2120885287442415671" />

**这是在说什么**

LLM 只是引擎，Agent 系统是整辆车：Gateway 接入、Orchestrator 编排、Permission Engine 控权、Audit Log 记录每一步。就像汽车有油门也要有刹车和黑匣子，否则不敢让它进生产环境。

**我们能学到什么**

- 任何涉及数据库写、付款、审批的操作，必须过 Permission Engine
- 任务执行必须带唯一 trace_id，贯穿日志、DB、消息队列
- 高风险操作（如删数据）默认进 Approval Queue，不可绕过

### AI Chat 系统不是 SSE 流式输出，是完整对话生命周期管理

<Tweet id="2121219696070729995" />

**这是在说什么**

Demo 只需前端+LLM API，生产系统还要管：断网后消息是否丢、刷新后上下文是否在、工具调用成功但消息未保存怎么办。就像聊天 App 不只是发消息，还得保证对方收到了、没重复、能撤回。

**我们能学到什么**

- 消息表必须带 status 字段（pending/sent/failed），不可仅靠 HTTP 成功
- 所有工具调用需生成幂等 ID，失败重试时复用 ID 防止重复执行
- 对话状态不能只存在内存，必须落库并支持跨实例同步

### LangChain 和 LangGraph 不是新旧关系，是能力层和编排层

<Tweet id="2121482431333282141" />

**这是在说什么**

LangChain 是「怎么让模型调工具」，LangGraph 是「怎么让工具调用不乱套」。比如 LangChain 做招聘 Agent，LangGraph 管它从解析简历→匹配岗位→生成报告→等 HR 审批的整个流程。两者像螺丝刀和装配线，各干各的。

**我们能学到什么**

- 简单任务用 LangChain create_agent 足够，别硬套 LangGraph
- 复杂流程（如需中断、恢复、审批）必须用 LangGraph 管状态
- Checkpoint 机制只保工作流状态，不保外部副作用（如已发邮件），需额外幂等设计

## 其他

### 先做一个垃圾出来，在 AI 时代更成立

<Tweet id="2120774019616285112" />

**这是在说什么**

过去写代码成本高，所以拼命想清楚再动手；现在生成代码快，但验证想法的成本更高。与其花三天设计完美架构，不如两小时做出粗糙原型，用真实反馈迭代。按常理理解是：AI 降低了试错门槛，但没降低判断门槛。

**我们能学到什么**

- 用 AI 快速产出可体验产物，比写详细 PRD 更早暴露问题
- 保留所有废弃分支和原型，它们是后续决策的关键依据
- 每次迭代后问：这个版本比上个版本多解决了哪个具体问题？

### 冒烟测试样板：用两道题快速验证模型+规则组合

<Tweet id="2121245277999026269" />

**这是在说什么**

它不测模型通用能力，只测「模型能否正确应用本仓私有规则」。比如一道题回放真实 MR，一道专测纪律（如禁止某类 import）。失败能直接归因到模型、Harness 或规则缺失。

**我们能学到什么**

- 冒烟集必须全自动、单题≤10 分钟，否则没人坚持跑
- 每道题配隐藏检查（如静态分析），防模型抄现成代码蒙混过关
- 结论只有三种：配置可用 / Harness 需修 / 模型能力不足

### AI e2e 测试：用自然语言下指令，用 API 数据当真值

<Tweet id="2121456182183551028" />

**这是在说什么**

传统 e2e 测 DOM，AI e2e 测意图。比如「生成上月报表」，Agent 自己找按钮点，但断言不看页面，而是查后端 API 返回的真实数据，再用独立 Judge 模型比对屏幕渲染是否一致。本质是把「UI 是否显示」换成「业务是否达成」。

**我们能学到什么**

- 测试用例用自然语言写，不绑定 selector 或 test-id
- 断言必须基于后端 API 数据，而非前端渲染结果
- 失败时自动打包轨迹包（日志+截图+推理上下文），供 Coding Agent 直接修 Bug

### Browser Use 的苦涩教训：模型进步比我们设计快

<Tweet id="2121117011556343965" />

**这是在说什么**

团队花一年优化 DOM 解析和浏览器操作，结果新模型直接理解截图+OCR+网页结构，绕过了所有精心设计的交互逻辑。按常理理解是：底层能力突变时，过度工程化的适配层反而成累赘。

**我们能学到什么**

- 避免为特定模型能力定制过深的胶水层
- 优先用模型原生支持的能力（如多模态输入），再补缺失环节
- 每季度审视架构中哪些模块已被模型原生覆盖

## 系统设计

### AI 让写代码变容易，但系统设计反而更难

<Tweet id="2120773569588477995" />

**这是在说什么**

AI 能秒出 CRUD，但不会告诉你：视频生成失败后该重试还是告警？用户重复提交会不会扣两次款？这些对应的是幂等设计、状态机、消息队列、链路追踪——底层工程知识没过时，只是使用场景变了。

**我们能学到什么**

- 每个功能上线前，先写三行故障预案：超时怎么办、失败怎么办、重复怎么办
- 用 Tracing 工具（如 OpenTelemetry）代替 print 日志定位瓶颈
- 学分布式知识，不是为了造轮子，而是读懂云服务商的错误码含义
