这周没追新模型，反而在翻旧账：怎么让 Agent 不瞎折腾、怎么用好 PostgreSQL 当缓存、还有那些被 AI 掩盖但没消失的工程问题。

## Agent 怎么落地

### 画图不用 Mermaid，一句话生成自包含 SVG 图

<Tweet id="2111967815297028106" />

**这是在说什么**

diagram-design 是个 Agent 技能，把「画个时序图」这种模糊需求转成 HTML+SVG 文件，不依赖外部服务。它把审美规则写死：只用一种强调色、坐标对齐 4 的倍数、自动提取网站配色——相当于把设计约束编码进技能里。不是让 AI 自由发挥，而是给它一套可执行的视觉规范。

**我们能学到什么**

- AI 画图的关键不是 prompt 多强，而是把设计规则变成机器可执行的约束
- 自包含 HTML+SVG 比 Mermaid 更易嵌入、调试和分享

### XERJ 让 AI 先查 GitHub 开源代码再写

<Tweet id="2111810791661781365" />

**这是在说什么**

XERJ 把相似开源项目下载下来建本地索引，AI 写代码前先搜已有实现，而不是纯靠参数生成。测试显示：相比 grep 搜源码，它生成的 token 少了 62%，说明更聚焦、更少废话。按常理理解是——它把「抄作业」这件事标准化、自动化了。

**我们能学到什么**

- AI 编程不是从零造轮子，而是高效复用已验证解法
- 本地代码索引比向量检索更准，尤其对语法结构、边界条件

### Graphify 把整库代码变知识图谱，边都可解释

<Tweet id="2112381606560420221" />

**这是在说什么**

Graphify 把代码、SQL、PDF 等全解析成 AST，再连成知识图谱——每条边代表‘这个函数调用了那个类’或‘这张表被这个 SQL 查询’，不是黑盒向量匹配。相当于给 Agent 配了张带路标和街道名的地图，而不是让它靠嗅觉找路。

**我们能学到什么**

- 大仓库喂给 Agent 前，先做静态分析建图谱，比直接扔文本靠谱
- AST 图谱能回答‘谁改了这个字段’这类精确问题，RAG 很难做到

### Agentic RAG 不是升级版 RAG，是不同任务类型

<Tweet id="2112629920207925385" />

**这是在说什么**

普通 RAG 是‘一次检索+回答’，适合单点问题（如‘报销政策是什么’）；Agentic RAG 是让 Agent 动态决定要不要拆问题、换数据源、重试，适合多跳问题（如‘今年报销变化+影响部门+特殊流程’）。关键区别不在技术炫酷，而在任务是否需要规划能力。

**我们能学到什么**

- 别为加 Agent 而加 Agent，先判断任务是否真需多步决策
- Agentic RAG 的代价是延迟高、token 多、失败路径复杂，要测清楚再上

## 岗位现实

### 面试官问：AI 生成 SQL 怎么防越权？

<Tweet id="2112386580786651164" />

**这是在说什么**

只给 SELECT 权限根本不够，因为用户可能查到不该看的列或行。正确做法是：① 专用只读账号 + 白名单表/列；② AI 只输出结构化查询计划，后端解析语法树，白名单校验后再生成参数化 SQL；③ 数据权限必须由后端按登录态动态加 WHERE 或列过滤，不能靠前端或数据库视图兜底。

**我们能学到什么**

- AI 生成 SQL 必须过‘解析-校验-生成’三道关，不能直执行
- 数据权限必须后端强制注入，且粒度到列和行

### Code Review 不会消失，只是审查对象变了

<Tweet id="2113462822332150140" />

**这是在说什么**

人不会逐行审 AI 生成的代码，但必须审它的输入（prompt）、输出约束（schema）、调用链路、错误处理策略和权限控制逻辑。就像以前审 PR，现在审的是 Agent 的‘行为说明书’。

**我们能学到什么**

- Code Review 重心从语法转向意图、边界和安全契约
- 不看代码 ≠ 不懂代码，得能读懂 AI 行为背后的工程假设

### 阮一峰周刊说‘好代码’概念正在消失

<Tweet id="2113522725855822069" />

**这是在说什么**

这条信息量一般，当冷知识即可。AI 生成的代码只要能跑通、接口稳定，人类是否易读已不重要。但注意：‘好代码’消失 ≠ ‘好系统’消失——后者仍取决于并发、容错、可观测性等老问题。

**我们能学到什么**

- 别纠结代码风格，但必须守住系统级质量红线
- AI 写代码快，但判断它是否可靠慢，这才是新瓶颈

### AI 工程师必须懂的 50 个基础概念

<Tweet id="2113664376481935668" />

**这是在说什么**

比如事务 ACID、N+1 查询、幂等性、熔断器、消息队列——它们不时髦，但决定了系统在真实流量下会不会崩。AI 可以帮你写一行 Redis.set()，但你得知道为什么这里要加锁、超时设多少、失败怎么重试。

**我们能学到什么**

- AI 是放大器，不是替代品：它放大的是你的工程判断力
- 能跑通 Demo ≠ 能扛住故障，重点练异常场景下的归因和验证能力

## 缓存别背八股

### PostgreSQL 用 UNLOGGED 表当缓存，真能代替 Redis？

<Tweet id="2113870416880238624" />

**这是在说什么**

UNLOGGED 表关掉预写日志，数据只存在内存缓冲池，写入快到 0.08ms（Redis 是 0.05ms），且断电清空，天然适配缓存语义。关键是：业务更新和缓存清理可放进同一事务，彻底消灭双写不一致。但它扛不住几十万 QPS，也不擅长排行榜、布隆过滤器等专用结构。

**我们能学到什么**

- 中小项目优先用 UNLOGGED 表+本地事务做缓存，省实例、保一致性
- Redis 不可替代的场景就三个：超高并发吞吐、自动内存淘汰、专精数据结构
