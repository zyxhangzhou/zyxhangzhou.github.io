RAG 不是万能胶水，Agent 不是自动流水线。这周读到的几条，都在讲一个事：模型再强，也得靠人设计好它该在哪一步干啥、读什么、信什么。

> 收集区间：2026-10-25 – 2026-11-01（JST），共 10 条。

## Agent 怎么落地

### Harness Engineering 是让 LLM 在生产里不胡说八道的兜底层

<Tweet id="2114325601326649846" />

**这是在说什么**

Harness 就像给大模型套上安全带和刹车——它不改模型本身，而是用状态图控制流程、加自愈逻辑处理工具失败、用可观测性追踪每一步。不是让模型自己想怎么跑，而是规定它必须按图索骥、出错就回滚、失败就重试。这条强调：API 调得好不等于系统稳，真正值钱的是把模型‘关进笼子’的能力。

**我们能学到什么**

- 别只练 prompt，要学怎么画状态图、设超时、加 fallback
- Harness 不是新框架，而是一套工程习惯：所有非确定性环节都必须有可观测+可干预出口
- 开源课里 8 个实战项目比概念更重要，建议从 Claude Code 运行架构那节动手

### TradingAgents 把交易公司分工直接搬进多智能体系统

<Tweet id="2114618783000375414" />

**这是在说什么**

Multi-Agent 不是多个模型随便聊天，而是按真实岗位分角色：分析师并行干活、研究员正反方辩论、风控和基金经理层层审批。它用日志存历史决策+实际收益+反思，让下一轮决策能读到‘上次为啥亏了’；回测时严格按当日已披露数据，不偷看未来。按常理理解是：多智能体的价值不在数量，而在是否复刻了人类组织里的制衡与反馈。

**我们能学到什么**

- 多智能体设计第一问：这个分工在现实中是否存在？有没有信息隔离或审批链？
- 记忆不是存聊天记录，而是存决策依据+结果+反思，三者缺一不可
- 开箱即用不等于免配置，支持多家模型只是起点，关键看它怎么统一处理各家输出格式差异

## RAG 别背八股

### 企业知识库不该把所有问题都塞进向量数据库

<Tweet id="2115253594291425528" />

**这是在说什么**

向量检索擅长找语义相近的文本，但不保证数字准确、枚举完整或条件合规。比如查门店销售额，业务数据库里已有结构化字段，何必导出 PDF 再切块嵌入？RAG 不是替代 SQL 的工具，而是补充——文档类问题走 RAG，精确统计走 DB，实时状态走 API。模型该做的是理解用户意图、选对工具、解释结果，而不是硬着头皮猜数字。

**我们能学到什么**

- 接到需求先画数据来源图：PDF？DB？API？各自权限和更新频率如何？
- 生成 SQL 只是第一步，执行前必须过权限校验、字段白名单、结果行数限制
- 混合架构不是技术炫技，而是让每个数据源发挥所长：向量查‘是什么’，DB 算‘是多少’，API 拿‘现在是什么’

### PageIndex 用文档目录树代替向量检索，像人翻书一样找答案

<Tweet id="2115251753956544655" />

**这是在说什么**

跳表（Skip List）是链表加多层索引，B+ 树是磁盘友好的平衡树，它们都靠结构加速查找；PageIndex 类似思路——不把文档切成块算相似度，而是抽标题建树，让 LLM 沿着‘第4章→4.2节→4.2.3小节’逐级下钻。适合年报、合同等有清晰层级的文档，但对聊天记录无效。它提醒我们：检索目标不是‘最像的文本’，而是‘能回答问题的正确证据’。

**我们能学到什么**

- 验证前先自查：文档是否有两级以上标题？单章内容能否一次读完？
- 不必二选一，可先用目录树缩到 2–3 章，再在这些章内跑向量检索
- 摘要不能全靠模型生成，人工核对 1–2 句‘这节管啥’比调 embedding 阈值更省时间

### IBM 新检索架构让幻觉减少 65 倍，关键是先过滤再生成

<Tweet id="2114979460495872355" />

**这是在说什么**

传统 RAG 是‘扔一堆材料给模型，让它自己挑’，结果材料错模型也跟着错；IBM 的方案像图书管理员——先检查每份材料是否相关、是否可信、是否过期，只把通过审核的喂给模型。这不是换 embedding，而是加了一层主动过滤机制。65 倍下降不是玄学，是把‘检索’从‘找相似’变成‘证真伪’。

**我们能学到什么**

- 下次 RAG 效果差，先别调 chunk size，试试加一层 relevance filter
- 过滤规则可以很简单：时间是否在有效期内？来源是否被授权？字段是否齐全？
- 生产环境 RAG 必须带‘拒绝回答’能力，宁可空回也不编造

### PageIndex 实测：目录导航比向量检索更准，但只适用于有结构的文档

<Tweet id="2115815053484048832" />

**这是在说什么**

它把文档标题转成树，每节点配人工核对过的 1–2 句摘要，提问时让 LLM 沿树下钻。实测 80 页手册里问‘退货例外条件’，向量检索多次命中相似词但错章节，目录导航一次到位。但它对无标题的聊天记录无效，且每次提问多调 2–3 次 LLM。四条自查满足就值得试：有两级标题、单章可一次读完、能接受多调用、愿意先用 5 题小范围验证。

**我们能学到什么**

- 验证成本极低：抽标题建树 + 手写摘要 + 5 个问题测试，半天可跑通
- 摘要必须人工核对，模型自动生成的‘第3章 运营’这种抽象描述毫无导航价值
- 现有 RAG 不用推倒，加一层目录预筛即可，改动最小

## 岗位现实

### 程序员的技术价值，得有外部可见的作品来证明

<Tweet id="2115679606107939063" />

**这是在说什么**

代码写得再好，如果全锁在公司内网，离职时就只剩简历上几行模糊描述。个人 IP 不是当网红，而是把项目复盘、踩坑记录、可脱敏工具代码、架构取舍理由，变成 GitHub 仓库、X 帖子、技术文章。这些东西积累三五年，会自然形成一套‘能力证据链’。

**我们能学到什么**

- 每周花 1 小时，把当天解决的一个真实问题写成 300 字短记，发 X 或存 Notion
- 开源不求大，一个能跑通的 CLI 工具 + README 说明适用场景，就比 10 个 demo 项目更有说服力
- 关注者质量比数量重要：200 个同行开发者，比 2 万泛粉更能带来真实机会

### 技术自嗨解决不了真实问题，客户买的是结果不是 HTTP 200

<Tweet id="2115687100888875060" />

**这是在说什么**

API 调通、视频生成成功、Agent 流程跑完——这些只是技术完成态。客户要的是字幕不抖、画面不糊、退货政策解释无歧义、报表数字和财务系统一致。技术人容易卡在‘我能做’，但商业闭环卡在‘用户愿不愿付钱’。中间差的是产品判断、成本意识和交付标准。

**我们能学到什么**

- 每次开发前，和客户确认一句：‘你验收成功的三个具体标准是什么？’
- 把‘接口返回成功’从测试用例里删掉，换成‘客户能用这个结果做什么动作？’
- 学点基础商业常识：LTV/CAC、毛利率、交付周期，比多背两个框架更能帮你判断项目值不值得做

## 其他

### React 里复杂状态别用 useState，改用 useReducer 加 lint

<Tweet id="2115797935401369801" />

**这是在说什么**

useState 适合开关、输入框这类简单状态；一旦涉及多字段联动、异步更新、撤销重做，就容易漏同步或状态不一致。useReducer 强制所有变更走 dispatch，配合 lint 规则（如禁止直接修改 state），相当于给状态流装上检查点。AI 时代更要防它随手塞一堆 local state 导致维护地狱。

**我们能学到什么**

- 新项目默认用 useReducer，简单场景再降级为 useState
- 加一条 ESLint 规则：禁止在组件内声明超过 3 个 useState 变量
- 状态变更必须带 type 和 payload，哪怕只有 1 个字段也要写清楚意图
